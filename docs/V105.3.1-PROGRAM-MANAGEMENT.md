# V105.3.1 — Program management

Administrators can now prepare timetable data through **Programs → Details → Manage Program**, without typing records or IDs into Google Sheets. The compact grid has six sections: Subjects, Levels, Modules, Classes, Teachers and Learners. Each row has Edit, Save and Cancel, with keyboard saving, filtering, archive/reactivation and retained edits after failures.

## Setup and acceptance

1. Keep the live Pages project on `main` and its last accepted production deployment. Use the separate `maktab-development` Pages project and `devrebootworker` for this revision. Both must deploy the same feature branch.
2. Retain existing Worker variables/secrets and the existing Program coordinator binding. This revision needs no new Cloudflare binding or Durable Object migration. Confirm Worker health version `105.3.1`.
3. Open https://maktab-development.pages.dev/programs/ using a central GLOBAL_ADMIN account. Complete Program registration and Prepare spreadsheet if still pending. The Program spreadsheet must grant the Development service account Editor access.
4. Open **Manage Program**. Select **Prepare management tables** once on an existing V105.2 Program. It adds the management history table and validates the other table headers; it does not replace existing data. Preparation is also available in the timetable.
5. Link an existing shared subject. If a name is missing, expand **Subject missing from the Academy list?** and create it with the existing central subject service, then link it. Subject names are shared across the Academy.
6. Optionally create levels under that Program subject. Add modules with or without levels. A module can only use a level belonging to its own subject.
7. Add classes, e.g. Year 1 and Year 2. Class name and academic-year label are separate from subject levels.
8. Assign existing active Academy accounts as teachers. Add existing learners to classes with a required From date and optional inclusive Through date. Overlapping memberships for the same learner/class are rejected; membership in different classes is allowed.
9. Open the timetable and choose the newly saved module, classes and teacher. Save, reload, validate, preview and publish a lesson shared by two classes. Check teacher, class and known-learner clashes. Archive/reactivate a record and verify current validation changes while published history retains its snapshot.
10. Test a failed save with retained edits, stale rows in two administrator sessions, and keyboard/mobile use. Use the retry/recovery controls rather than editing state rows in Sheets.

New Programs default to `Africa/Johannesburg`. Program setup and timetable timezone fields are dropdowns. New timetables inherit the Program timezone, falling back to Johannesburg if pending; saved timezones, saved pending choices and interrupted-save payloads are preserved.

## Storage and authorisation

Both management writes and timetable writes run through the existing per-Program coordinator, with fresh central GLOBAL_ADMIN checks inside the queue. A management save writes one immutable `ProgramManagementState` revision plus its operation receipt atomically to the Program spreadsheet. Revisions have a monotonic sequence, actor AccountID and timestamp. Retries reuse the operation ID and exact payload. Read views select the highest sequence, so a delayed old write cannot replace newer management data.

The initial V105.2 reference tables remain a baseline. Before the first management save, they supply the records. After that, the latest management snapshot is the authoritative reference view for the management screen and timetable. The snapshot holds ProgramSubjects, ProgramLevels, ProgramModules, ProgramClasses, ProgramEnrollments and ProgramTeachers. Do not edit baseline tables to change managed data: use the screens. Snapshots are bounded to 40,000 characters; exceeding the current bound rejects a save without partial changes. Larger-scale storage remains future work.

Program teacher assignments link existing central AccountIDs. Existing central TEACHER/SENIOR/ADMIN grants remain eligible until an explicit Program assignment overrides their timetable eligibility. Assigning or archiving a teacher here does not create accounts, change PlatformRole, modify UserCourseAccess, or enable a login/teaching workspace. Central inactive accounts cannot be newly assigned and cannot be selected to teach. Full account provisioning, role management and learner-facing access remain later stages. This distinction avoids granting additional central privileges simply to populate a timetable dropdown.

Shared subject creation reuses the existing central global-subject endpoint and its audit/policy rules. It is an Academy-wide change and is labelled accordingly. Program saves never rename shared subjects. Existing operational Reboot sheets, central account credentials and immutable published timetable snapshots are preserved.

## Recovery and rollback

An uncertain save is held in browser session storage. **Retry same change** repeats that exact mutation. **Recover interrupted change** reconciles the coordinator journal. Unsaved local edits are retained after recovery; download the row and explicitly discard/reload before reapplying it. A stale revision or changed Academy reference blocks a save.

Do not downgrade a Program back to V105.2 after management edits without a planned data rollback: V105.2 does not read management snapshots. Retain the V105.3.1 reader and the history/receipts for Programs already using management. Back up Development spreadsheets before upgrade. Resolve any pending operation before reverting code. Live production remains on its accepted release.
