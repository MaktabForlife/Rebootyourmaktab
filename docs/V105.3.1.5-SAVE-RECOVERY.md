# V105.3.1.5 — Management save recovery

## Behavior

Refresh records preserves the active row, its original baseline and the exact pending operation. Draft typing is saved in session storage and restored on a same-tab browser reload. Cancel remains an explicit discard. Refresh no longer opens a discard/download/re-entry workflow.

The backend supplies per-row revision hashes. A save checks the edited row against its original revision and validates selections against fresh reference data. Unrelated rows or central catalogue/account changes do not block it. Legacy clients retain whole-snapshot checks. Sheet row-position metadata is excluded from row hashes.

A row conflict performs a three-way comparison of the original record, the user's entry and the latest saved record. Independent field changes merge and retry automatically once. Overlapping changes show both versions, with Save my version and Discard my edits and use saved version. An overwrite still checks the reviewed revision, so subsequent changes cannot silently disappear. Deleted rows remain visible as drafts and are not recreated silently.

Interrupted or uncertain saves attempt recovery and retry once automatically. Their operation IDs and payloads stay unchanged. Persistent failure keeps the pending save and offers Retry same change. Pending saves also resume when the page is reopened in the same tab. A successful save followed by a failed refresh is reported as saved, rather than retried as an uncertain write. Existing catalogue and bulk import workflows remain available.
