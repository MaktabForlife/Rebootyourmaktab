# V105.3.1.1 — Academy curriculum subjects

Program subjects now use a separate Academy curriculum catalogue. The GlobalSubjectList used by Global Courses is no longer the source of new Program subject choices. Reboot continues using its own SubjectList; this release copies reviewed names, not operational records or curriculum content.

## Use the screens

1. Open Development Programs, select the Program and open **Manage Program → Subjects**.
2. Choose **Add subject**. Select an existing Academy name, or **Create a new subject…**, enter the name and **Save**. New names are created and linked to this Program in the same screen.
3. Optionally expand **Import subject names from Reboot**. Choose **Review Reboot subjects**, tick the active names needed and **Import selected names**. This populates the shared catalogue; use **Add subject** to link chosen names to this Program.
4. Existing Global-based Program links show **Review needed**. Choose **Edit**, select or create the appropriate Academy subject, then **Save**. ProgramSubjectID is preserved, so attached levels and modules stay attached. Review the timetable draft before republishing; old published snapshots stay unchanged.
5. A subject already linked to the Program cannot be added twice. Edit/reactivate the existing Program row. A confirmed Academy subject link cannot be changed into a different subject; archive it and create another link.

Levels remain optional and scoped to a subject within a Program, independently of class academic-year labels. Modules remain the units selected by the timetable.

## Deployment and storage

Deploy matching frontend and Worker from the feature branch to **maktab-development** and **devrebootworker**. No new Worker bindings, secrets or Cloudflare class migration are required. The existing coordinator class adds a separate catalogue RPC and SQLite journal. A catalogue-specific instance per Platform spreadsheet serializes catalogue writes; Program timetable coordinators remain separate.

The first subject creation/import automatically prepares **AcademySubjectList** and **AcademySubjectOperations** in the configured Platform spreadsheet. Read-only screens do not create tables. The service account needs Editor access to that Platform workbook. Reboot import reads only SubjectList from the explicitly configured GOOGLE_SPREADSHEET_ID; it never accepts a user-supplied workbook target. Import needs read access to this configured Development Reboot workbook. Reboot and Platform must have different spreadsheet IDs.

Only GLOBAL_ADMIN accounts can read or write the catalogue. Authority is checked again inside the coordinator. GlobalSubjectList and its courses, resources and permissions remain unchanged. Creating a subject grants no teaching or login rights.

## Retry and compatibility

Names are matched using normalized case and whitespace; concurrent creations or imports of the same name reuse a canonical subject. Import previews carry a source revision; source edits require a new review. Imports select at most 250 active source rows per action and record the source-ID-to-Academy-ID mappings in their operation receipt. Imports do not automatically synchronize later Reboot edits or rename anything in Reboot.

Catalogue writes and their receipts are committed atomically to fixed Sheet coordinates, with a durable pending intent before the write. Catalogue rows are append-only in this release; delayed retries cannot replace newer records. Use **Retry same import/change** after an uncertain response. **Recover subject catalogue** resolves a blocked catalogue intent without discarding your pending request. Program save recovery remains available separately.

Creating a name and linking it spans two workbooks and therefore is not one atomic transaction. The screen retains the creation operation and link request in session storage and resumes them without duplicating the name. If the Program changes during this flow, linking stops for review; the new name remains available in the Academy catalogue and can be selected after reload. No saved Program links are automatically migrated. Legacy references remain readable until explicitly mapped; new Global-based links are rejected.

Do not roll back the Program reader to V105.3.1 after creating Academy links: that reader cannot resolve Academy subject IDs. Retain this reader or plan an explicit data migration. Do not edit the managed catalogue or old Program reference tabs directly; manual row deletion/reordering can invalidate recovery coordinates. The 40,000-character Program management snapshot limit is unchanged.

Public release labels and Worker health use **105.3.1.1**. npm package metadata uses the valid semantic version **105.3.1-1** for the same release.

## Acceptance checklist

- Create a new name through Add subject and verify it appears as a saved Program subject.
- Reuse the same name in another Program; verify there is one Academy catalogue entry.
- Review/import selected Reboot names; repeat the import and verify duplicates are reused.
- Verify a Global Course entry is not offered for a new Program subject.
- Map a Review needed row and verify its levels/modules and existing publication history remain intact.
- Add a module with no level and choose it in a timetable draft.
- Confirm Program setup still defaults new Programs to Africa/Johannesburg.
- Retry an interrupted save using the same action; verify one catalogue subject and one Program link.

## Verification

Extended API integration covers authorization, catalogue separation, reviewed import revisions, active source selection, case/whitespace duplicates, concurrent creates, lost responses, blocked-intent recovery, authority revocation, source mapping receipts, explicit legacy remapping, dependent records and immutable publication history. It also compares Reboot and Global data before/after to confirm isolation. The same integration passes in Cloudflare's local runtime with the actual RPC and SQLite journal. Browser verification uses synthetic fixtures only; real data acceptance is performed through the deployed screens.
