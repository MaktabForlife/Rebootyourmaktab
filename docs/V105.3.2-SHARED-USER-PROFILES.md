# V105.3.2 — Shared academy user profiles

Superseded by [V105.3.2.1 academy matrix setup](V105.3.2.1-ACADEMY-ACCESS-MATRIX.md): the new matrix is separate, Free/Paid is a scope policy, and setup roles do not alter legacy access. The older subscription-confirmation behavior below is historical.

## Scope and decisions

One academy identity is reused across global subjects and programs. The User profiles screen at `/users/` supports adding users, editing names, setting account Active / Inactive and assigning multiple roles per subject/program. It is accessible from the academy account chooser, Program setup and each management User profiles row. Dated class memberships remain in Program management.

The roles/subscription column combines User (free) or Student (paid) with any combination of Teacher, Senior and Admin. New Student grants require an explicit administrator confirmation of a paid subscription for that specific subject/program. This is a manual access record, not payment collection or billing automation. A free global subject cannot receive a paid Student grant. Staff roles alone do not imply payment or subscription access.

Active / Inactive is a separate account field. Inactive blocks personal-account access throughout the academy and removes timetable teacher eligibility while preserving identity, roles, subscriptions, class memberships and history. The administrator cannot deactivate their own account, and the model protects the last active academy administrator. Reactivation restores retained assignments. New roles cannot be granted to an inactive account or inactive scope.

Every shared-profile read, sign-in-link lookup, save and recovery requires a current academy administrator (`GLOBAL_ADMIN`) account. Authority is checked again inside the serialized write queue. Subject/program Admin is scoped and does not confer academy-wide role-management permission. This screen cannot grant `GLOBAL_ADMIN`, change a PIN/hash or replace a personal sign-in identity. New users receive a new stable identity and personal sign-in link with PIN setup incomplete; no message is sent.

## Existing records and storage

Read-only inspection of the supplied development platform workbook found 33 unique AccountIDs in GlobalSubjectAccessMatrix and the same 33 in UserAccounts. The matrix contains subscription/access flags, not names or staff-role definitions. UserAccounts therefore remains the single profile directory; existing identities and links are retained.

- `UserAccounts`: display name, active status and existing central identity/credentials. Existing profile writes touch only name, active and modification-audit cells.
- `UserCourseAccess`: one retained row per account/program/role. Removed grants become inactive; legacy CourseRecordIDs are preserved.
- `GlobalSubjectAccessMatrix`: existing subscription flags remain authoritative for paid global subjects. Changes update only the chosen account/subject cell.
- `AcademySubjectRoles`: retained Teacher/Senior/Admin rows per account/global subject, separate from paid flags.
- `AcademyProfileOperations`: durable operation receipts, request hashes and safe acknowledgements for retries.
- `PlatformAuditLog`: actor, operation, target and role/subscription change audit.

The two new tabs are created atomically with the first actual profile save if missing. New accounts and their matrix rows are created in the same batch. No workbook migration or synthetic test records are pushed into the actual academy workbook by deployment.

## Save and recovery behavior

Profile writes are serialized per academy workbook through a dedicated instance of the existing SQLite coordinator binding. The coordination unit is the shared workbook because profile/grant creation allocates rows in its shared tables. Reads and unrelated Program coordination are separate. Intent is persisted before spreadsheet writes; profile changes, audit and receipt are one Sheets batch. Exact operation IDs and payload hashes prevent duplicate identities/grants after a lost response.

Profiles and assignments have separate comparison revisions. Changes made elsewhere require a visible saved-versus-draft choice before overwrite. Credentials and login dates are excluded from profile-edit revisions and never overwritten by profile updates. Drafts and uncertain operations survive refresh, navigation and page reload. A confirmed acknowledgement updates the local display, including a new user's role controls, before refreshing. A failed refresh retries reads only; quota errors wait at least 60 seconds, with bounded retries. Configuration and changed-storage errors retain the pending operation for review.

Recovery checks stored target-row identities, headers and written cells before applying old coordinates. A moved or externally changed row blocks recovery without writing; restore/review the affected spreadsheet before retrying. Google Sheets has no conditional multi-range update: these checks are not transactional isolation from simultaneous direct spreadsheet edits or older writers. Avoid editing/reordering the same records directly during a pending save. Existing legacy subscription/identity tools remain separate writers; unifying them with this coordinator is a follow-up.

## Deliberate boundaries

Generic program Teacher/Senior/Admin grants already feed timetable teacher selection. Program teaching workspaces remain in the timetable/integration phases. Global-subject staff roles are recorded by this release; subject-specific staff workspaces and their permission consumers remain future work. The existing subscription delivery path continues to use the canonical matrix and active account status.

Reboot uses existing staff/student records in its separate legacy workbook. This screen can pause or reactivate an already linked role, but it will not invent a CourseRecordID or copy a teacher mapping into a student role. Additional Reboot staff/student records must first be created through its existing workspace. Academy profile creation itself is available here. Separate legacy Reboot login tokens are validated against legacy staff/student records; central account deactivation or scoped-role removal does not revoke those independent logins. Manage their status in Reboot until authentication is consolidated. The screen makes this distinction visible.

Individual student module-completion history remains planned for V105.5, separately from class progress, with permanent student/program/module identities, completion date and recorded-by identity. Future stages remain V105.3.3 timetable development, V105.4 library/resources and V105.5 student/program integration and tasks.
