# V105.2 — Program timetable builder

V105.2.0 adds module-based timetable building to V105.1 Program setup. The local preview uses synthetic Aalimiya modules, classes, teachers and dates. No actual teaching dates, timezone, curriculum levels or teacher assignments have been inferred from the supplied book list. Live Development acceptance is still required.

## Using the builder

Open **Programs → Details → Open timetable** as a central GLOBAL_ADMIN. Complete V105.1 Program registration and spreadsheet preparation first. Choose **Prepare timetable tables** once; this creates empty reference and timetable tables without touching the Setup tab or existing Reboot data.

Set the publication timezone and From/Through dates. Add a lesson row, choose a module, one or more classes and an authorised teacher, then choose recurring weekdays or a one-off date. One-off lessons use the same first/last date. Times display as `13h00`. Tab moves between cells; Ctrl/⌘ + Enter saves the draft. The class selection stays in one lesson row even when Year 1 and Year 2 learn together.

**Save draft** preserves incomplete work and leaves the published timetable unchanged. **Validate** reports incomplete references and teacher/class/known-learner overlaps. **Preview publication** uses the same server rules as Publish, with a weekly calendar and an all-occurrences list. Select a calendar lesson to return to its draft row. Edits invalidate the preview. **Publish this timetable** explicitly creates a new immutable version and makes it current. Publish revalidates current module/class/teacher references and stale revisions.

Add an exception using the original lesson and occurrence date. Cancel preserves the original anchor; Move changes the actual date/time while retaining that anchor. All moved dates must remain in the publication window. Published history retains the labels and audiences that applied when published, even if catalog labels change later. Student/Academy delivery is connected in V105.6; no new student route reads the draft.

## Minimal references for this stage

Full membership and curriculum editors remain V105.3/V105.4. Populate only verified minimal references in the prepared Program spreadsheet during controlled Development setup. Synthetic examples are in `scripts/program-timetable-fixtures.mjs` and are never written by the application’s preparation action.

| Table | Required reference |
|---|---|
| ProgramSubjects | Stable ProgramSubjectID, this CourseID, existing shared GlobalSubjectList.SubjectID, Active |
| ProgramLevels | Optional LevelID scoped to ProgramSubjectID, name, sort order, Active |
| ProgramModules | Stable ProgramModuleID, ProgramSubjectID, optional LevelID, name, sort order, Active |
| ProgramClasses | Stable ClassID, this CourseID, name, optional academic-year label, Active |
| ProgramEnrollments | Optional known dated ClassID/AccountID memberships; StartDate required, EndDate inclusive or blank, Active |

A module’s optional level must belong to that same Program subject. Shared subject names come from the Platform’s existing GlobalSubjectList. Teachers come from active central UserAccounts with an active TEACHER, SENIOR or ADMIN grant for this Program in UserCourseAccess. Platform administration alone does not create a teaching assignment. Prepare creates no grants or accounts.

Known learner conflicts use effective membership dates and deduplicate learners within a combined lesson. Empty membership data is disclosed in validation. Cross-Program teacher conflicts await the later Academy integration; this release does not claim to check them.

## Deployment prerequisites

1. Retain the accepted V105.1 files and back up affected Development spreadsheets. Apply this changed-files overlay at the repository root. A separate cumulative overlay is provided for the V104.5.4 baseline.
2. Run `npm ci` in backend using the included lockfile. The tested Wrangler version is recorded in verification. Keep existing secrets/variables and the existing compatibility date; changing unrelated runtime semantics is outside this stage.
3. Deploy the matching frontend and Worker to Development using the configured development environment. The Worker entrypoint is now `src/worker-runtime.js`, which exports the original fetch handler plus `ProgramTimetableCoordinator`.
4. The `PROGRAM_TIMETABLE_COORDINATOR` Durable Object binding and `v1052-program-timetable` SQLite class migration must be included. Both production and development configurations declare the binding; their namespaces remain environment-specific. Missing bindings fail closed for writes.
5. Confirm health version `105.2.0`, central GLOBAL_ADMIN access, V105.1 mapping/identity, backend Editor sharing and timetable preparation. Enter the verified minimal references, then test a real shared lesson under controlled Development acceptance before enabling any later stage.

The Durable Object stores only coordination metadata for one in-flight change per Program. Canonical drafts, publications, receipts and the current-pointer history remain in Google Sheets. This is not the later D1 migration. Do not bind two independent coordinator namespaces to the same Program spreadsheet; all application timetable writers for a workbook must use its one namespace. Do not manually edit, sort, delete or relocate state/publication/receipt rows during operation or recovery.

## Failed saves and recovery

The browser retains a mutation’s operation ID and exact payload in session storage until it receives a definite result. If the response is uncertain, editing is temporarily locked and **Retry same change** resends that exact operation. A completed operation returns its stored receipt instead of duplicating publication.

**Recover interrupted change** completes the already authorised pending intent or recognises its completed receipt. It requires fresh GLOBAL_ADMIN authority; the original actor remains recorded in the receipt. It never invents a new timetable. After recovery, local edits are kept; download a copy and reload the saved revision before reapplying them. A conflict/stale response retains edits and offers **Download draft** plus the explicit discard/reload choice.

The per-Program coordinator serialises requests, rechecks authority inside its queue, records a durable write intent before external I/O, and blocks different mutations until that intent is resolved. One Google batch writes the draft revision, publication when applicable, and operation receipt. Replaying uses fixed row coordinates. State is append-only with a monotonic sequence, so a delayed older network write cannot replace a newer pointer or draft. Ordinary lesson occurrences are still derived; append-only state rows are revisions, not materialised teaching sessions.

If the Program mapping, headers or stored IDs are damaged, stop editing and restore the affected workbook from backup with the coordinator quiescent. Preserve its pending journal until the original intent is reconciled. Do not delete the Durable Object or wipe receipt/state rows as a retry mechanism. Restore code and data together for rollback; preserve publication IDs/anchors already used by later teaching records. V105.1 configuration edits still require one setup editor at a time; V105.2 coordination applies to timetable writes only.

Limits: 100 rules, 200 exceptions, 366 publication days, 1,000 derived occurrences per preview and 40,000 characters per stored JSON snapshot. Same-day time intervals only. Skipped/ambiguous DST times block publication and require an explicit unambiguous exception. These limits bound reads, validation and Google cell size; they are not a 60-user capacity claim.
