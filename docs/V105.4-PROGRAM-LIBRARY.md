# V105.4.1.3 — Program curriculum and Library

The Program Library runs on `feature/105.3.4.13`. It uses Reboot's eBooks, Printables, Audio, Video and Other categories. Resources are attached to a Program subject and optionally a level, module and task. eBooks may have an author, publisher, ISBN, publication year and cover image. V105.4.1.1 made device uploads resumable after temporary rate limits; V105.4.1.2 restored Save resource after an upload; V105.4.1.3 adds teacher uploads, shared Drive file copying and one Resources folder for all Programs.

## Teacher and administrator workflow

Open the Program Library from the Academy account page. Choose **Add resource**, select a category and subject, and optionally a level, module and task.

- **Add from device** opens the local file picker. Confirm **Upload to Resources** in the centered dialog. The Library Google account owns the uploaded copy.
- **Add from Google Drive** opens the centered dialog. Paste a file link or ID after sharing the original file with the Library Google account, then choose **Copy into Resources**. The original remains in the teacher's Drive. Files already in Resources can also be selected there.
- Review the resource details and choose **Save resource**. An upload or copy is a separate Drive operation, so an unsaved resource may leave a file in Resources.

A teacher, senior or Program administrator must have an active role in the Program's Academy access matrix. The signed-in Academy account may currently be in another Course context; the Library checks Program access directly. A global administrator can manage every Program. The Library link on the Academy account page lists accessible Programs. Program student access remains a later stage.

## Resources folder

`SystemConfig!ProgramLibraryDriveFolderId` identifies the one Resources folder for all Programs. New device uploads and shared file copies always go there. Only a `GLOBAL_ADMIN` can change it on the Library page. The Library Google account needs permission to add files; the Worker service account needs permission to read them. Keep General access **Restricted**. After changing the folder, run `authorizeM4LServices` in the Development Apps Script editor to confirm that its deploying account can add files. Earlier folder IDs are retained in `SystemConfig!ProgramLibraryPreviousFolderIds` so previously saved resources remain readable.

The Worker checks the Program and resource type before signing a short-lived request to Apps Script. Apps Script uses the deploying account's Drive authorization to start device uploads or copy a teacher-shared file. The Google OAuth token and `M4L_LIBRARY_BRIDGE_SECRET` stay on the server. The Worker checks the final file's category and folder when the resource is saved. Existing resource rows and old Program Library roots remain readable.

## Development setup and checks

Synchronize the complete repository `apps-script/code.gs` to the Development Apps Script project and deploy a new web-app version. Keep `appsscript.json` as deployed already; it includes the required Drive and external-request scopes. The Worker needs `APPS_SCRIPT_URL` and the same `M4L_LIBRARY_BRIDGE_SECRET` that is stored as an Apps Script Script property. Do not put the secret in Sheets or browser code.

1. Confirm `authorizeM4LServices` reports `libraryCanAddFiles: true` for the configured Resources folder.
2. Sign in as a Program teacher. Upload a small PDF from the device, save the resource, reload and preview it. Then share a PDF with the Library account, copy it from its Drive link and save it.
3. Try a cover image and the book metadata. Confirm the file and cover appear in Resources and the book details survive reload.
4. Confirm the teacher cannot change the Resources folder or prepare Library tables. Check a global administrator can change the destination without losing access to existing resources.
5. Confirm unsupported file types, a file not shared with the Library account and an outside-folder file ID cannot be saved. Check Reboot and Global Library access still works.

`main` and production remain unchanged until this branch is accepted. Local synthetic tests do not modify real Sheets or Drive files; live Development acceptance remains necessary.
