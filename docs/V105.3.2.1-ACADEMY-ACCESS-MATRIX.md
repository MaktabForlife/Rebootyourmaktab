# V105.3.2.1 — Academy access matrix setup

## Agreed behavior

The initial structure lives in Google Sheets. Use it to settle the user matrix before migrating to Cloudflare D1 (assumed meaning of “d2”). This release does not provision D1 or move authorization to the new matrix.

User profiles at `/users/` is a shared academy screen: one row per account, name and Active/Inactive columns, then one column per program or global subject. Desktop keeps name/status visible while scrolling across scope columns. Mobile uses labelled rows and a separate visible settings area. A cell can combine Student, Teacher, Senior and Admin; an empty role set is displayed and stored as User. User is a default, not an additional grant alongside higher roles.

Each scope header edits Free/Paid. Free permits every active user; Paid permits Student, Teacher, Senior or Admin. An inactive account or inactive scope is denied under the proposed policy. This is an access classification, not payment processing, proof of payment, or subscription expiry tracking. There is no paid-subscription confirmation checkbox for assigning Student. Policy changes require confirming their scope-wide effect. All read, link, save and recovery endpoints require a current academy administrator (`GLOBAL_ADMIN`). A scoped Admin never grants academy-wide authority or role-management rights.

Matrix role values are `USER`, one role, or canonical pipe-separated combinations such as `STUDENT|TEACHER`. Name/status formulas look up UserAccounts by AccountID; never by display name or physical row position. Edit these through the profile screen to preserve their single source. IDs, formulas and sheet headers are structural; native dropdowns constrain the editable choices. Application validation rejects unknown roles, malformed headers, duplicate identities, invalid policies or non-SETUP stages. A setting cannot activate migration just by changing a sheet cell.

“Set up / update matrix” adds missing users/scopes without re-importing or overwriting reviewed cells. New scope columns retain stable IDs and extend an existing native matrix table. Direct edits to the source systems after the import are not continuously mirrored into setup roles. Before cutover, perform a fresh reconciliation of both sources and resolve discrepancies.

## What changes access now

**Matrix roles and Free/Paid settings are SETUP only.** Global Subjects, Reboot, generic program access and timetable teacher eligibility continue reading their current authorization records. The screen explicitly states this. No legacy identity or CourseRecordID mapping is invented by a new matrix role.

Profile name and Active/Inactive edits still update UserAccounts immediately. Deactivation blocks central account sessions while retaining all roles/history. The current administrator cannot deactivate themselves, and at least one academy administrator must remain active. Independent legacy Reboot logins still need to be managed in Reboot. New profiles receive a stable account and default-User matrix row; an empty legacy global access row is also created for identity consistency, granting no paid access. Credentials, PIN hashes, existing links and academy-admin flags cannot be edited through profile fields.

## Saves and concurrency

The existing academy coordinator serializes saves, checks fresh administrator authority, persists intent, then writes changes, audit and receipt in one Sheets batch. Profile, cell and scope-policy revisions detect stale edits. Recovery guards original sheet identity, headers, row identity and fields being written, including structural changes, before replaying coordinates. Direct edits to Sheets are not transactionally locked by this queue; do not reorder/edit the same records during pending saves.

Drafts and exact pending requests survive reload. Confirmed saves update the display before reading fresh records. A quota-limited refresh retries reads only, waiting at least 60 seconds; it cannot duplicate an acknowledged save. Genuine conflicts show saved and draft values with an explicit replacement choice. Cached clients using the old role-save format receive a refresh instruction instead of silently writing legacy access.

## Later D1 mapping (design, not a deployed migration)

| Current data | Proposed normalized database tables |
| --- | --- |
| UserAccounts | `accounts`, primary key existing AccountID; authentication data handled in a separately reviewed identity migration. |
| AcademyAccessScopes | `access_scopes`, primary key ScopeKey, unique type + source ID, policy, activity and revision. |
| Matrix role cells | `account_scope_roles`, composite key AccountID + ScopeKey + role. Split canonical pipe values into rows; User is the absence of elevated roles. |
| AcademyAccessReview | `access_reviews`, composite key AccountID + ScopeKey, original source value and review/actor/timestamps. |
| Operation receipts / audit | `access_operations` and append-only `access_audit`, retaining operation IDs and safe result hashes. |
| UserCourseAccess legacy links | Separate `legacy_identity_links`; preserve CourseRecordIDs and reconcile missing staff/student identities before authorization cutover. |

Use foreign keys and role/policy constraints, stable identifiers, comparison revisions and transactions. The UI and policy model should remain storage-independent. Do not use names, sheet row numbers or newly generated replacement account IDs as migration keys. Keep subscription billing/expiry records distinct if introduced later; the current Paid label is not a financial ledger.

Sequence: finalize and accept Sheets structure → confirm import reviews and policies → snapshot both matrices and compare proposed versus existing access for every account/scope → resolve legacy identity links and permission consumers → test reversible development cutover → migrate validated records to D1 with count/referential checks and reconciliation → switch storage/authorization only after acceptance. Avoid uncontrolled dual writes. Production remains a separate, explicitly authorized rollout.

Individual student module-completion history remains a future learning record keyed by student/program/module, with completion date and recorder; it must survive role changes and account deactivation. Class progress is not a substitute.
