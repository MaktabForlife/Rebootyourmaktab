# V105.1 — Program setup

Release: **105.1.0**. Baseline: Development V104.5.4, commit `5938c988cb5b589e1637b08f5c68c41115f2a0b7`.

This release implements Program registration and configuration through a compact, editable grid at `/programs/`. A platform administrator can create a Program, enter its duration and timezone, save a draft, archive it, and prepare/check its separate Google spreadsheet. Reboot remains in its current workspace. New Programs remain inactive for learners.

The implementation is locally verified and ready for Development deployment review. It has **not** been pushed, deployed or connected to the real Platform spreadsheet. The real Aalimiya spreadsheet has not been registered or prepared by this release.

## What the administrator sees

Open the personal Academy account link, sign in as a platform `GLOBAL_ADMIN`, then choose **Manage Programs**. The link also appears when that global administrator is using an existing Program context. Local Program administrators, teachers and students cannot use the setup service.

The grid supports inline fields, search, status filters, row Save/Discard, visible unsaved/saved/error states, Tab navigation and Ctrl/⌘ + Enter to save a row. Failed saves retain entered values. Refresh offers an inline choice to keep editing or discard changes. Leaving the page invokes the browser's unsaved-change protection; browser-specific confirmation behavior still needs beta verification. On small screens, the table scrolls horizontally and identifying columns stop sticking so all actions remain reachable.

Duration is descriptive. Entering four years does not create four curriculum levels or assign classes to years. A blank timezone is visibly pending. No calendar, syllabus or teaching policy is invented.

**Check readiness** reads the selected spreadsheet through the application's own credentials. **Prepare spreadsheet** creates its minimal identity tab and is repeatable. An inaccessible or incompatible sheet is not overwritten. Preparation does not publish lessons or enable teaching.

Only Configuration is enabled. Timetable, membership, curriculum, library, attendance, progress and planner capabilities are shown as later stages and cannot be enabled through the API. Their configurable policies and operational activation remain in the planned stages.

## Development setup

1. Back up the Development Platform spreadsheet and the Aalimiya spreadsheet. Preserve current Worker/Pages deployment versions for rollback.
2. Apply this changed-files package over the verified Development baseline. Deploy the backend and matching frontend to **Development**, using the existing project deployment process. No new bindings or secrets are required.
3. Confirm the existing backend service account has Editor access to the separate Aalimiya spreadsheet. Connector access from Codex does not demonstrate application access. Do not expose a private key in the browser or enter it in a sheet.
4. Sign in using the platform administrator's personal Academy link. Open **Manage Programs → New Program**.
5. Enter **Aalimiya**, **4** years, and this spreadsheet link: [Aalimiya Development](https://docs.google.com/spreadsheets/d/1fjtGSiHGxvhpi3Nu7Frpc1O27tIDuQhiVFNp81jZlWw/edit). It is in the user-selected [Aalimiyah Development folder](https://drive.google.com/drive/folders/1ioNkTsyPjJ22PoFhFrnco25UhPAltqH5). Leave timezone pending until the teaching timezone is confirmed. Keep status **Draft**.
6. Save the row. On first creation the service prepares the additive `ProgramDefinitions` tab in the Platform spreadsheet, then atomically writes the registry entry, definition and audit record in that spreadsheet.
7. Select **Prepare spreadsheet**, then **Check readiness**. The target receives only `ProgramIdentity`; its original `Setup` tab is preserved. Timezone may still be pending, and teaching remains disabled.
8. Refresh and verify the saved name, four-year duration, fixed mapping and readiness. Verify a local Program ADMIN cannot create or edit a Program. Check existing Reboot login, Academy, library and teaching workflows before stage acceptance.

Do not change `CourseRegistry.Active` manually for a new Program. Setup uses `SchemaVersion=105.1-program` and `Active=FALSE`. Student profile resolution and operational activation are deliberately later work. Do not replace the existing Reboot registry row or `GOOGLE_SPREADSHEET_ID` with the Aalimiya sheet.

## Recovery and concurrency limits

- A failed registration leaves no partial registry/config/audit write: those three operations are one Sheets spreadsheet batch. An empty `ProgramDefinitions` tab may remain after an earlier preparation step; a retry repairs it.
- A create request keeps a stable UUID while the draft is open. Retrying after a lost response returns the existing matching Program. If the browser was closed, refresh/search before creating again; the spreadsheet mapping cannot be registered twice through sequential requests.
- If preparation fails after registration, the Program stays inactive. Fix application sharing and retry **Prepare spreadsheet**. Missing, empty and header-only identity tabs are repairable. Populated incompatible headers, another Program's identity or existing operational tables are refused.
- A save with an old revision is rejected. Copy any edits you need before using **Discard and refresh**, then reapply them to the current row. If a save response was lost, refreshing reveals whether it committed.
- **V105.1 setup requires one administrator editing at a time, including browser tabs.** Revision comparison is not a distributed write lock. Concurrent requests can race between validation and commit; simultaneous saves/registrations are not supported in this stage. Duplicate identifiers are detected and subsequent editing fails closed. Coordinated concurrent mutations must be implemented and tested before concurrent setup use; timetable publication coordination remains V105.2.
- Sheet mappings are immutable in this screen, including for archived Programs. Moving a Program's records needs a separate migration; a rename is safe because identities are stable.
- Do not manually sort or edit the Platform data during setup writes. IDs are authoritative; row coordinates are resolved only for the current write.

Rollback code by restoring the prior Worker and Pages release. Leave new registry rows inactive and retain the additive tabs and records for investigation or a later retry. Do not delete audit history or remove only one half of a registry/definition pair. No existing Reboot table needs a schema migration or restoration unless it was separately changed outside this release.

## Local preview

From the repository root, run `node scripts/program-builder-preview.mjs`, then open `http://127.0.0.1:8105/programs/`. The server listens only on the loopback interface. It uses synthetic records in memory and makes no external calls. The yellow preview banner includes an intentional one-shot failed-save control. Restarting the process resets its records.

The preview uses the real configuration service and actual frontend files, with an in-memory storage adapter and a synthetic login response. It does not prove live authentication, Google sharing, deployment configuration or production capacity. The real Worker routes and Google transport behavior are separately exercised in automated tests with mocked Google responses.
